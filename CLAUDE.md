# Aura - API Platform Project

## Overview

Aura is built on **API Platform**, a Symfony-based framework for building API-first applications. It uses a monorepo structure with three main components: a PHP API backend, a Next.js PWA frontend, and Playwright E2E tests.

## Project Structure

```
Aura/
  api/                # Symfony/API Platform backend (PHP 8.4+)
  pwa/                # Next.js frontend (React/TypeScript)
  e2e/                # Playwright end-to-end tests
  helm/               # Kubernetes/Helm deployment charts
  docs/               # Project documentation
  .github/            # GitHub config (templates, workflows, policies)
  compose.yaml        # Docker Compose (dev environment)
  CHANGELOG.md        # Project changelog
  CODE_OF_CONDUCT.md  # Contributor code of conduct
  LICENSE             # GNU AGPL-3.0 (dual-licensed; commercial license available)
  CLA.md              # Contributor License Agreement (enables dual licensing)
```

## Tech Stack

### API (Backend)
- **Framework**: Symfony 7.2 with API Platform 4.x
- **PHP**: >= 8.4
- **Database**: PostgreSQL 16 (via Doctrine ORM)
- **Server**: FrankenPHP
- **Real-time**: Mercure (WebSocket-like push)
- **Testing**: PHPUnit
- **File storage**: league/flysystem-bundle (local adapter in dev, swap to S3 later via `api/config/packages/flysystem.yaml`). User-uploaded media lives under `/app/var/media/` in the container, served by Caddy at `/media/*`.
- **Image processing**: intervention/image (GD driver). See `api/src/Service/ImageUploadService.php`.
- **Media model**: `MediaObject` entity is the shared upload target for any domain entity that needs files. Used by `User.avatar`, `Task.attachments`, and `Space.attachments`. Uploads go through `POST /media-objects` (multipart), then entities link them via IRI. Sensitive bytes (kind=attachment) stream through the gated `GET /media-objects/{id}/download` endpoint, which re-checks owner / task-readability / space-membership before serving. Avatar bytes stay on the public `/media/...` Caddy route. Project-level attachments were collapsed up to the space — shared files now live at `space_attachment`, so every project + member in a space sees one shared file pool managed in the space detail's Files tab.
- **Spaces (#181, #185)**: Top-level container for content. Every user gets a non-deletable personal "Private" space at signup; additional shared spaces can be created and shared with users / `UserGroup`s. Roles are `admin` and `member` — admins manage members, edit metadata, and delete the space; members can read/write content and edit/delete only their own. `Space`, `SpaceMembership` (direct user, unique on space+user), and `SpaceGroupMembership` (transitive via group, unique on space+group) live under `api/src/Entity/`. PR 1 ([#181](https://github.com/roboparker/Aura/issues/181)) provisioned the entities, `/spaces` CRUD (admin-gated writes via `SpaceCreateProcessor` + entity-level `isAdmin(user)` security expressions), `SpaceAccessExtension` (EXISTS-subquery scoping mirroring `ProjectAccessExtension`, with both direct and group-inherited membership), and the backfill that links every existing project / discussion / CFD to its creator's personal space. PR 2 ([#185](https://github.com/roboparker/Aura/issues/185)) is the behavior change: every access predicate, security expression, and project-membership check across the API now goes through space membership instead of the old `project.members` collection (which is dropped along with the `project_member` table; `Version20260507120000` backfills any pre-existing project members into `space_membership`). Helpers: `Space::hasMember(user)` / `isAdmin(user)` (UUID-based comparison so they survive `EntityManager::clear()`), `Space::getEffectiveUsers()` (deduped union of direct + group members), `Project::isAccessibleBy(user)` / `isSpaceAdmin(user)` / `getEffectiveMembers()`, `Task::isAccessibleBy(user)` (owner OR project's space includes user; standalone tasks remain owner-only). For DQL, `App\Doctrine\SpaceMembershipDql::userBelongsToProjectSpace($projectAlias)` returns the direct-or-via-group EXISTS fragment so the same boilerplate isn't copy-pasted across access extensions, the media-download controller, the task repository's reorder query, and the MCP tools. Access matrix: read/list any space member; create any space member (Project's `Post` accepts `space === null` so the existing PWA — which doesn't know about spaces yet — keeps working, the processor defaults it to the caller's personal space); edit any space member; delete = creator OR space admin (Project) / author OR space admin (Discussion); pin/lock Discussion + CRUD on CustomFieldDefinition = space admin only. Discussion is parented directly by `Space` (no project link). `CustomFieldDefinition` denormalises its parent project's space via `PrePersist` (`syncSpaceFromProject`); `ProjectSpaceDefaultListener` auto-fills `Project.space` for direct-EM persistence (tests, fixtures, future CLI). Personal-space invariant enforced at the DB by partial unique index `uniq_space_personal_per_user` on `space (created_by_id) WHERE is_personal = true`. The personal "Private" space is created in `UserPasswordHasherProcessor` post-persist so the membership row and space row land in the same flush as the user — a half-failed signup can't leave an orphan space behind. `POST /projects/{id}/members` is preserved as a thin shim that adds the resolved user to the project's space (role `member`) so the existing PWA keeps working until PR 4. Test helpers live in `App\Tests\Api\SpaceMembershipFixture` (`addProjectMember()` / `ensureSpaceMembership()`). PR 3 space invites ([#186](https://github.com/roboparker/Aura/issues/186)) is described under "Group + space invites" above. PR 4 ([#187](https://github.com/roboparker/Aura/issues/187)) shipped the active-space PWA UX: `pwa/contexts/ActiveSpaceContext.tsx` loads the user's space list from `GET /spaces`, exposes `{spaces, personalSpace, activeSpace, setActiveSpace, refresh, isActiveSpaceAdmin}`, and persists the choice in localStorage under `aura.activeSpaceId` (falls back to the personal space when the persisted choice is no longer accessible). `pwa/components/common/SpaceSwitcher.tsx` adds the dropdown next to the Aura wordmark with a Lock icon for personal spaces. `/spaces` (index) and `/spaces/{id}` (detail with members, invite-by-email form, pending invites list with revoke, and admin-only Delete) are the management surface; the navbar's "Manage spaces" link drops you into them. `/projects` and `/discussions` listings append `?space={iri}` to scope to the active space; new projects POSTed from `/projects` pin themselves to the active space's IRI so a user in a shared space doesn't accidentally drop new work into their personal one. Owner-gating in `DiscussionsPanel` and `CustomFieldsManager` is replaced with `isSpaceAdmin` derived by looking up the project's parent space in the already-loaded space list (no extra fetch). Project detail page drops the per-project add-member form (members are space-level now) and surfaces a "Space" badge plus "Manage members in space" link. The `?space=` SearchFilter on Project + Discussion lives behind the `space:read` group on the User entity (so the User row embedded inside `SpaceMembership.user` serializes with email/name/avatar fields the PWA needs).
- **Groups**: Reusable named user-sets (`UserGroup` entity exposed as `/groups` — API short name `Group`; the entity uses the `UserGroup`/`user_group` prefix because `group` is a reserved SQL keyword and `Group` clashes with `Symfony\Component\Serializer\Attribute\Groups`). Owner has full control (edit metadata, manage members, transfer ownership, delete); other members are read-only. `UserGroupAccessExtension` filters listings to groups the current user owns or belongs to (DQL joins through `memberships`); non-member item lookups return 404. **Membership is a first-class join entity** (`UserGroupMembership`, table `user_group_membership`, unique on `(user_group_id, user_id)`) carrying a `joinedAt` per member — it replaced the old plain `user_group_member` ManyToMany so the detail UI can show a "Joined" column. There is no `role` column: owner-vs-member is derived from the `owner` FK. `UserGroup` helpers `getMembers()` (derived `Collection<User>` for the many call sites that count/iterate members — Space access, invite flows, the transitive-membership DQL fragments which all join `...userGroup.memberships m ... m.user = :user`), `hasMember()` (UUID-based, survives `EM::clear()`), `addMember()`/`removeMember()` (create/remove membership rows). Extra fields: `color` (palette-validated, nullable → UI falls back to the owner's `personalizedColor` via `resolveGroupColor`), `slug` (stable `g-`-prefixed handle generated once from the title by `UserGroupOwnerProcessor`, unique, read-only — direct-persist sites like fixtures/tests must `setSlug()` themselves), and `updatedAt` (Gedmo Timestampable). `getAttachedSpaces()` (a `group:read` getter) walks the inverse `SpaceGroupMembership` collection and emits a flattened `{id,name,color,isPersonal,ownerColor,role,since}[]` for the detail page's "Attached to" card. **Endpoints** (all in `UserGroupMemberController` unless noted): `POST /groups/{id}/members` (owner add-by-email — existing user → direct membership, unknown → invite); `DELETE /groups/{id}/members/{userId}` (owner removes a member; the owner can't be removed); `POST /groups/{id}/leave` (member self-removal; owner can't leave); `POST /groups/{id}/transfer` (owner hands off to another member — **step-up protected via `SensitiveActionVerifier`**: TOTP when 2FA is on, else `currentPassword`; the old PATCH-`owner` path is gone, `owner` is no longer in `group:write`). `DELETE /groups/{id}` itself is **step-up protected** through `UserGroupDeleteProcessor` (same TOTP-or-password gate as space delete, since deleting a group revokes its members from every attached space). `GET|DELETE /groups/{id}/invites[/{id}]` + `POST /groups/{id}/invites/{id}/resend` (rotate token + re-send) in `UserInviteController`. **PWA**: `/groups` index (`PageHeader`-style header + search, onboarding empty state, "Owned by you" / "Member of" tables with member avatar stacks, owner chip, `N spaces` badge, last-updated dot via `isRecent`, row `…` menu for delete/leave), `/groups/new` (mirrors `/spaces/new`: name + description + `ColorSwatchPicker` + `EmailChipInput`), and `/groups/{id}` detail (header with role badge + meta line, members table with role/joined/remove, add-member row, pending-invites with resend/revoke, sidebar About / Attached-to / At-a-glance cards, danger zone, owner-vs-member views, `TransferOwnershipDialog` step-up). Shared bits: `GroupTile` (colored square + grid glyph, mirrors `SpaceTile`), `resolveGroupColor` in `pwa/lib/avatarPalette.ts`, types in `pwa/lib/groupTypes.ts`.
- **Group + space invites**: One `UserInvite` per email (unique) collects every pending attachment for that address: `GroupInvite` rows for groups, `SpaceInvite` rows for spaces (#186). Tokens are sha256-hashed like `PasswordResetToken`; the plaintext is only ever in the email. Add-by-email: `POST /groups/{id}/members` (owner-only) and `POST /spaces/{id}/members` (admin-only) — each branches on whether the email matches an existing user (direct membership) vs unknown (upsert + invite). `App\Service\InviteMailer` renders the signup-link email with the union of every group + space currently attached, qualified as `group "X"` / `space "Y"` so a recipient invited to both gets one coherent message; token rotation on every send keeps the most recent email authoritative. Public lookup at `GET /invites/{token}` returns `status` (`'pending' | 'expired' | 'accepted'`), `email`, `expiresAt`, and an `inviter` chip (`{name, email, initials, color}`). Pending responses also include `groups[]` (each with `memberCount`) and `spaces[]` (each with `role`). The PWA's `InviteSignup` component (`pwa/components/auth/InviteSignup.tsx`) branches on the status — pending renders the accept form with the invite-context list above it, `expired` shows the "ask the sender for a new link" card with a mailto fallback, `accepted` shows the "this invite was already used" card, and a signed-in viewer whose email doesn't match the invite email gets the mismatch screen. 404 still means an unknown token. Admin/owner management lives at `GET|DELETE /groups/{id}/invites[/...]` and `GET|DELETE /spaces/{id}/invites[/...]`; revoking the last attachment on a `UserInvite` removes the parent so a token can't redeem to nothing. When the invitee signs up via the link (`POST /users` with `inviteToken`), `UserPasswordHasherProcessor` walks both `groupInvites` and `spaceInvites` and attaches the new user — provided the signup email matches the invite email.
- **Custom fields (#227)**: Per-project schema (`CustomFieldDefinition`). Storage shape is `(kind, subtype, config, footer, nullable)` — `kind` is the top-level family (`boolean`/`text`/`numeric`/`date`/`select`/`reference`), `subtype` the specialisation (e.g. `numeric.money`, `select.multi`, `reference.user`), `config` the per-kind JSON payload (options, min/max, currency, multi, …), `footer` an optional `{kind, label?}` aggregation descriptor, `nullable` the inverse of the legacy `required` flag (kept as a denormalised mirror column for now). Per-kind editor + validator logic lives in `api/src/CustomField/Type/` behind `CustomFieldTypeInterface`: each (kind, subtype) is one strategy class, auto-tagged `app.custom_field_type` and resolved through `CustomFieldTypeRegistry`. Adding a new kind is a one-class drop on both sides of the wire (PHP strategy + matching TS entry in `pwa/components/custom-fields/kind-editors.tsx`). Definitions are space-admin managed (CRUD at `/custom_field_definitions`); reads scoped via `CustomFieldDefinitionAccessExtension`. The PWA mounts `CustomFieldsManager` (`pwa/components/custom-fields/`) on `/projects/{id}/custom-fields`: kind/subtype dropdowns swap in the matching config editor (currency for money, min/max for numeric/date, structured options list for select, length + regex for text). Per-task values live on `CustomFieldValue`, embedded as `Task.customFieldValues` (`{definition, value}` pairs) — clients write the whole array via the Task `task:write` group and orphanRemoval reaps anything dropped. The `(task_id, definition_id)` unique constraint is `DEFERRABLE INITIALLY DEFERRED` so PATCH's delete-then-insert collapses cleanly. `ValidCustomFieldValues` (class-level constraint on Task) dispatches through the strategy registry — top-level invariants (project-scope, no dup definition, required-when-not-nullable) stay in the validator; per-value shape rules live on each strategy. Companion `ValidCustomFieldDefinition` (class-level on CFD) dispatches `validateConfig()` + checks `footer.kind` against the strategy's supported aggregations. Money values are `{amount: int-minor-units, currency: ISO-4217}` with the currency pinned on the field's `config`; reference values are IRIs scoped to the field's space (`reference.user` walks `space.getEffectiveUsers()`; the rest compare `target.space === field.space`). The FTS projection on `custom_field_value.value_search` is written by `CustomFieldValueSearchSubscriber` calling `strategy.searchText()` on persist/update so references serialize their target's display label and money emits `<amount> <currency>` — `search_vector` then derives from `value_search` via STORED generated column. Legacy `CustomFieldDefinition::setType()` / `setOptions()` remain as internal entity helpers (no `#[Groups]`, off the wire) so test seeders and the migration backfill still speak the old labels; the canonical API contract is `{kind, subtype, config, nullable}`. Reference subtypes are `user`/`task`/`project`/`page`/`discussion` — `reference.project` (`ProjectReferenceStrategy`) scopes to projects in the field's space like the others. **PWA redesign**: `CustomFieldsManager` renders the schema as a drag-to-reorder table (NAME · KIND · REQUIRED · FOOTER · FILLED) backed by `@dnd-kit`; create/edit/delete happens in a right-side `CustomFieldSheet` drawer (our `ui/sheet.tsx`) with rich per-kind editors in `kind-editors.tsx` (searchable currency `Combobox` + derived decimals + live money preview, live regex pattern-check for text/url, `Calendar` date-range bounds, `@dnd-kit` select options with per-option color swatches + usage counts, reference target-type cards). Required + multi are `ui/switch.tsx` toggles (base-ui Switch); footer aggregation is a `NONE|COUNT|SUM|AVG|MIN|MAX` pill row + label override. Supporting endpoints (all space-access scoped, 404 for outsiders): `POST /projects/{id}/custom_field_definitions/reorder` (space-admin only, renumbers `position` contiguously — `CustomFieldDefinitionReorderController`), `GET /projects/{id}/custom_field_stats` (`{total, stats:[{definition, filled}]}` for the FILLED column), `GET /custom_field_definitions/{id}/option_stats` (`{options:[{key,label,count}]}` per-option usage), and `GET /projects/{id}/custom_field_definitions/activity` (project-scoped change log — `CustomFieldDefinition` is Gedmo `Loggable`, served via `CustomFieldDefinitionActivityController` + the shared `ActivityFeedSerializer`, surfaced in the `CustomFieldChangeLog` drawer). The static ISO-4217 list for the money picker lives in `pwa/lib/currencies.ts`; decimal places are derived from the currency, not stored.
- **Custom-field footer aggregation (#227)**: `GET /projects/{id}/custom_field_footers` returns one row per CFD that has a `footer.kind` configured, with the aggregation computed over the filtered task list. Endpoint honours `?search=`, `?status=`, `?overdue=`, `?dueDate[before|after|strictly_*]` (Task collection filter subset). Numeric int/float/money push through SQL (`(value #>> '{...}')::numeric` + `SUM/AVG/MIN/MAX`), date kinds use lex MIN/MAX on the JSON-extracted text, every kind supports `count` of non-null values. Money returns `{amount, currency}` so the PWA's `CustomFieldFooterRow` (under the project task list) can format with `Intl.NumberFormat`. Multi-value sum/avg/min/max returns null in v1 — JSON array unroll is out of scope.
- **Task detail drawer (PWA)**: `/tasks` rows have an "open details" button (`PanelRight`) that opens `TaskDetailDrawer` (`pwa/components/tasks/TaskDetailDrawer.tsx`) — a **deep-linkable** right-side `Sheet` (the open task lives in the URL as `?task={id}` via shallow routing, so it survives refresh/share) with **Details / Activity / Comments** tabs. Details edits title/description/assignees/tags inline (PATCH `/tasks/{id}`), shows a due/recurrence/reminders summary (read-only for now — rich editors land in later phases), and renders the **custom-field VALUE editors**: `CustomFieldValueList` (`pwa/components/tasks/CustomFieldValueList.tsx`) loads the project's definitions and dispatches per (kind, subtype, multi) to `pwa/components/tasks/value-editors.tsx` (boolean→`Switch`, text/url/rich_text→`Input`/`Textarea`/chips, numeric→number input, money→amount input pinned to the field's currency, date/time/datetime→`Calendar`/native inputs, select→`Combobox` with option color dots, reference→`Combobox` scoped to the field's space/project). It persists the whole `customFieldValues` array (debounced, dropping empties so the server orphan-removes them) and surfaces inline 422s via `pwa/lib/violations.ts` (`parseViolations` → `propertyPath`-keyed map; `customFieldValues[i].value(.amount)` paths are mapped back onto each field row — a contract pinned by `TaskCustomFieldValueTest::testValidationViolationUsesCustomFieldValuesPropertyPath`). The drawer is non-modal with an `onInteractOutside` guard so in-drawer comboboxes/popovers (portaled to `<body>`) stay clickable, same as `CustomFieldSheet`. Activity/Comments/Attachments reuse the existing `ActivityPanel` / `CommentsPanel` / `AttachmentsPanel`.
- **Comments (#228)**: Single `Comment` entity at `/comments` covers tasks, pages, and discussions via a polymorphic parent — `commentable_type` (VARCHAR(16)) discriminates between `'task'` / `'page'` / `'discussion'`, and exactly one of the `task` / `page` / `discussion` FKs is set (enforced by `chk_comment_parent_exactly_one`). Threads are flat chronological — no reply tree. Adding a parent type is a copy-the-`page`-arm change across `Comment` (constants, FK + setter, `syncCommentableType`/`getCommentable`/`isAccessibleBy`/`isDeletableBy`/`validateParent`), `CommentAccessExtension`, `CommentMercurePublisher::parentIri`, `CommentMentionService` (`collectMentionableUsers` + `renderTitle`), `CommentsMercureTokenController`, and `McpEntitySerializer`. **Locked discussions reject *new* comments** (`Comment::validateNotLocked`, insert-only — existing comments stay editable/deletable; the PWA hides the composer behind a locked banner via `CommentsPanel`'s `canCompose`/`composerNotice` props). `@mention` tokens anywhere in `body` fire one `mention` Notification per resolved recipient through `CommentMentionService`, with the recipient set parent-aware: task comments resolve through `task.owner + project.space`; page and discussion comments through the parent's `space.getEffectiveUsers()`. Mercure live updates on every parent via `CommentMercurePublisher` (topic `<parentIri>/comments`); the subscription cookie endpoint covers `/tasks|pages|discussions/{id}/comments/mercure-token`. Access scoping mirrors the parent: `CommentAccessExtension` LEFT-joins through `task` / `page` / `discussion` and OR's the per-parent visibility check (task: owner or project-space membership; page / discussion: space membership). Delete-escalation also branches: task owner can delete on tasks, space admin can delete on pages and discussions; author can always delete their own. The PWA renders every surface through one shared `CommentsPanel` (`pwa/components/common/CommentsPanel.tsx`) and one live-update hook (`useCommentLiveUpdates`).
- **Notifications**: `Notification` entity at `/notifications` is a per-recipient inbox. Types: `task_reminder` (cron `DispatchTaskRemindersCommand`), `mention` / `reply` / `comment` (comment activity), `assigned` / `status` (task activity). Each carries an optional `actor` (who triggered it; null for system rows) and resolves a deep-link `target` (computed `getTargetUrl`/`getTargetLabel`/`getContextLabel` from whichever of `task`/`comment`/`discussion`/`page` is set — no extra fetch). **All event rows are created through one service, `App\Service\NotificationDispatcher::notify()`**, which enforces no-self-notification, the one-row-per-comment precedence `mention > reply > comment` (via the `uniq_comment_mention` index + a pre-check), and fans each row out to the live bell (Mercure) + Web Push (reusing `PushSenderInterface`) + a real-time email (`emails/notification.{html,txt}.twig`) when the recipient is on the `realtime` frequency. Digest-cadence users are skipped for the real-time email — `DispatchNotificationDigestCommand` (which only selects digest users) owns their delivery, so no one is double-emailed. Triggers: `CommentMentionService` (mentions) + `CommentActivityNotifier` (reply to prior thread participants, comment to the thread owner) fire from `CommentAuthorProcessor`; `TaskActivityNotifier` fires `assigned` (newly-added assignees, diffed via `TaskRepository::findAssigneeIdsFromDatabase` since `previous_data` shares the collection ref) and `status` (completion) from `TaskOwnerProcessor` (POST) + `TaskUpdateProcessor` (PATCH). Reads scoped to the recipient by `NotificationRecipientExtension`; client-writable fields are `readAt` + `archivedAt` (mark-read / archive); bulk `POST /notifications/mark-read` (`{ids}`/`{all}`) + `POST /notifications/archive` (`{ids}`) live on `NotificationBulkController` (routes carry `priority: 10` to beat the `/notifications/{id}` item route). Live bell: per-user private Mercure topic `/users/{id}/notifications` published by `NotificationMercurePublisher`, cookie minted by `NotificationsMercureTokenController` (`GET /notifications/mercure-token`). PWA: `NotificationBell` (navbar dropdown — tabs, time grouping, mark-all-read, live via `useNotificationLiveUpdates`, links to `/notifications` + `/settings/notifications`) and the `/notifications` full page (`pwa/pages/notifications/index.tsx` — tabs `NOTIFICATION_TABS`, `View archived`, bulk select + action bar, `NotificationRow` three-state component). Type colors/badges live in `pwa/lib/notificationTypes.ts` (`NOTIFICATION_META`); list/actions in `pwa/lib/useNotifications.ts`. Preferences (email/push/frequency) live on the Settings shell via `PATCH /me/preferences` (see **Settings** below).
- **Settings (account shell)**: The former split `/account` + `/settings` pages are consolidated into one **Settings shell** at `/settings` with a left subnav — `pwa/components/settings/SettingsShell.tsx` (shared chrome + auth gate) + `SettingsNav.tsx` (`SETTINGS_SECTIONS`). Sub-routes live under `pwa/pages/settings/`: **Profile** (`AvatarSection` + `EmailChangeForm` + `ProfileForm` + `TimezoneSelect` + `StartPageSelect`), **Security** (`ChangePasswordForm` + `TwoFactorSection` + `ActiveSessionsTable`), **Notifications** (matrix + digest + quiet hours), **API tokens** (`ApiTokensTable` + `CreateApiTokenDialog`), **Danger zone** (deactivate / export / delete). `/account` and `/settings` 307-redirect to `/settings/profile` via `pwa/next.config.js` `redirects()` (server-side, so old links + the post-login fallback resolve without a hydration hop); `signinHrefForCurrent`'s `FALLBACK_PATH` is `/settings/profile`. Auto-saved panels share `pwa/lib/usePreferencePersist.ts` (optimistic merge + request-id guard + transient `SaveIndicator`). **Time zone** is a preference: `'timezone' => 'UTC'` in `User::DEFAULT_PREFERENCES`, validated against `\DateTimeZone::listIdentifiers()` in `UserPreferencesController` (rides `/api/me` via `getPreferences()`); picker is a `Combobox` over `Intl.supportedValuesOf("timeZone")`.
  - **Start page (#406)**: `'landing' => ['page' => 'space', 'spaceId' => null]` in `User::DEFAULT_PREFERENCES` is the post-login landing destination (the workspace home with the personal space active — the #405 default). `page` ∈ `User::LANDING_PAGES` (`tasks`→`/tasks`, `notifications`→`/notifications`, `spaces`→`/spaces`, `space`→`/projects`); for `space`, a non-null `spaceId` must be a space the caller belongs to (`UserPreferencesController::validateLanding` does a `Space::hasMember` check; unknown + forbidden both 422 "404-shape"; a `spaceId` sent with any non-`space` page is normalised to null on store). Picker is `pwa/components/settings/StartPageSelect.tsx` (page radio cards + a space `Combobox` over `ActiveSpaceContext.spaces`; the personal space stores as `spaceId: null` so it stays the forgiving fallback, and a configured space that's no longer accessible shows a fallback note). The login flow (`SignInForm` / `TwoFactorChallengeForm` / `AuthCard`'s already-authed bounce) resolves the destination via `pwa/lib/landingDestination.ts` (`readLanding` + `landingPathFor`) and feeds it as `safeNextPath`'s fallback so an explicit `?next=` deep link still wins; the `space` choice also primes the active space through `ActiveSpaceContext.selectActiveSpaceById`. `login()` / `submitTwoFactorCode()` now return the fresh user payload so the redirect reads preferences without a re-render. Tests: `App\Tests\Api\UserPreferencesTest`.
  - **Active sessions**: `UserSession` registry (table `user_session`) keyed by `sha256(session id)`, upserted by `App\EventListener\SessionRegistryListener` on each authenticated `main`-firewall request (skips `^/mcp` + token auth — tokens aren't sessions). `UserSessionController` (`GET /me/sessions`, `DELETE /me/sessions/{id}`, `POST /me/sessions/revoke-others` — step-up via `SensitiveActionVerifier`); the listener 401s + invalidates a session whose row is revoked on its next request. `App\Service\UserAgentSummarizer` derives the device label.

- **Waitlist mode (launch gate)**: A runtime toggle that flips the instance between *open signups* and *waitlist mode*. State lives in the `app_setting` key/value table (`App\Entity\AppSetting`, read/written only via `App\Service\WaitlistSettings`; default when no row exists comes from the `app.waitlist_enabled_default` parameter — `true` in prod/staging, `false` in `when@dev`/`when@test` so local dev + the suite keep open signups). - **User segments (A/B tests, beta gating, rollouts)**: Instance-level (admin-managed, not space-scoped) cohorts. A user belongs to a segment when any rule matches, with explicit per-user overrides winning — precedence in `App\Service\SegmentEvaluator`: disabled → out; manual `exclude` → out; manual `include` → in; user roles ∩ `includedRoles` → in; deterministic rollout bucket (`hexdec(substr(sha256(key:userId),0,8)) % 100 < rolloutPercentage`, stable per user so raising the % never drops anyone) → in. Each segment exposes a synthetic role `ROLE_SEGMENT_<KEY>` (`Segment::keyToRole()` upper-cases the key + dashes→underscores; `roleToKey()` reverses it — keys are validated lowercase-no-underscore so the round-trip is lossless). Because membership is dynamic the role is never stored on the user: `App\Security\SegmentVoter` answers `is_granted('ROLE_SEGMENT_*')` live (affirmative strategy lets its GRANT beat the built-in RoleVoter's DENY for a role absent from the token), and `AuthController::serializeUser` appends the active `ROLE_SEGMENT_*` strings to `/api/me`'s `roles` (skipped for waitlisted accounts) so the PWA gates with the same role strings. `Segment` (`segment` table: `key`/`name`/`description`/`purpose` ∈ {beta,ab_test,rollout}/`enabled`/`rolloutPercentage`/`includedRoles` json/`createdBy`) + `SegmentMembership` (`segment_membership`, unique on `(segment_id,user_id)`, `mode` ∈ {include,exclude}) live under `api/src/Entity/`. `key` is settable only on create (`segment:create` group, unioned into the POST denormalization context) and read-only after, like a slug; a class-level `Assert\Callback` rejects `ROLE_SEGMENT_*` in `includedRoles` (no segment-on-segment gating). **Endpoints** (all ROLE_ADMIN, gated in `security.yaml` `^/segments`): `/segments` CRUD (`Segment` ApiResource, `SegmentCreateProcessor` stamps the creator) + `SegmentMemberController` — `POST /segments/{id}/members` (`{email, mode}`, existing users only — a re-POST flips the mode), `DELETE /segments/{id}/members/{userId}`, `GET /segments/{id}/preview` (exact reach + `{manualIncludes, byRole, byRollout, manualExcludes}` breakdown via `SegmentEvaluator::reach()`). **CLI**: `app:segment list|show|create|delete|enable|disable|rollout|roles|add|exclude|remove` (`App\Command\SegmentCommand`); - **Rate limiting (abuse throttles)**: the three unauthenticated endpoints are throttled — login (firewall `login_throttling` via the `app.login_rate_limiter` service: per-(IP, email) + per-IP sliding windows, only failed attempts consume, 429 + `Retry-After` via `App\Security\JsonLoginFailureHandler`), signup (per-IP, consumed in `UserPasswordHasherProcessor` before persist, throws `TooManyRequestsHttpException`), and forgot-password (per-IP + per-lowercased-email, consumed in `PasswordController::throttleForgotPassword` *before* the user lookup so 429s stay enumeration-safe). Limiters are declared in `api/config/packages/framework.yaml`; sizes are runtime env placeholders (`RATE_LIMIT_*`) with prod defaults in `api/.env` and effectively-unlimited overrides in `.env.dev`/`.env.test` (Playwright + PHPUnit register many users from one IP). `api/tests/Api/RateLimitTest.php` trips the limits by overriding `$_ENV` per test and isolating buckets with unique `X-Forwarded-For` IPs (127.0.0.1 is a trusted proxy in test, so the spoofed address becomes the client IP). Limiter storage is the filesystem cache pool — per-container state, fine for single-container deploys; multi-replica needs a shared store. The 2FA challenge keeps its separate per-user `two_factor_verify` limiter. See `docs/developer/password-reset.md` § Rate limiting.
- **2FA (TOTP)**: opt-in per user, powered by [SchebTwoFactorBundle](https://symfony.com/bundles/SchebTwoFactorBundle/current/index.html) (`scheb/2fa-bundle` + `scheb/2fa-totp` + `scheb/2fa-backup-code`). The `User` entity implements `TwoFactorInterface` and `BackupCodeInterface`. The TOTP secret is stored encrypted (sodium secretbox via `App\Service\TwoFactorSecretCipher`, key derived from `APP_SECRET`) and decrypted into a transient cache by `App\EventListener\UserTotpCipherInjector` on Doctrine `postLoad`. Setup/verify/disable/regenerate-codes/reveal-codes endpoints live at `/me/2fa/*` (controller: `TwoFactorController`); the login challenge piggy-backs on the bundle's firewall listener at `/auth/2fa-check`, with JSON request/response handlers in `App\Security\TwoFactorJsonHandler`. Verify-code attempts are throttled per user via the `two_factor_verify` rate limiter (5/min). Recovery codes are stored as sha256 hashes (one-time use; consumed code removed from the JSON list). **Step-up for sensitive self-service actions** (disable 2FA, regenerate or reveal recovery codes, change password) routes through `App\Service\SensitiveActionVerifier`: when 2FA is enabled the body must carry a `totpCode` (validated through the same per-user `two_factor_verify` limiter as login); when 2FA is off it falls back to `currentPassword`. A stolen cookie can't silently rotate the password or disarm 2FA without the authenticator device. The PWA branches the form input on `user.twoFactor.enabled` — `TwoFactorSection`'s disable/regenerate/reveal dialogs always render a TOTP input (they're only reachable when 2FA is on), and `ChangePasswordForm` swaps the password field for a TOTP one when 2FA is enabled. **Lost-device recovery**: signing in with a backup recovery code at `/auth/2fa-check` fires `BackupCodeEvents::VALID`, which `App\EventSubscriber\TwoFactorRecoveryListener` handles by flagging the session through `App\Service\TwoFactorRecoveryState` (`_2fa_recovery_pending` session attribute) and dispatching a "recovery code used" out-of-band email through `App\Service\TwoFactorRecoveryMailer`. While the flag is set, `SensitiveActionVerifier` accepts `currentPassword` even though 2FA is still on (the user has just proven they can't reach the authenticator), and the user payload at `/auth/2fa-check`, `/auth/login`, and `/api/me` carries `twoFactor.recoveryPending: true` so the PWA can mount `TwoFactorRecoveryInterstitial` (`pwa/components/auth/TwoFactorRecoveryInterstitial.tsx`, mounted from `Layout.tsx`). The forced modal offers two paths: **Set up a new authenticator** (POST `/me/2fa/reenroll` with `currentPassword` returns a fresh secret + QR; user POSTs the new TOTP to `/me/2fa/verify` to flip 2FA back on with a brand-new recovery-code batch) or **Turn off two-factor** (DELETE `/me/2fa` with `currentPassword`). Both branches clear the recovery flag and fire a confirmation email (`sendReconfigured` / `sendDisabled`). The dialog has no close affordance — Escape and outside-click are blocked so the user can't end up navigating with an active recovery flag still set on the server. Logout still tears down the session (and the flag with it) from the navbar.

- **Background jobs (job queue)**: Asynchronous work runs through **Symfony Messenger** with the **Doctrine transport** — a Postgres-backed queue (`messenger_messages` table, created by migration `Version20260606130000`, `auto_setup=false`) drained by a long-running worker (`bin/console messenger:consume async`). Needs both `symfony/messenger` and `symfony/doctrine-messenger` (the `doctrine://` transport factory lives in the latter). Config in `api/config/packages/messenger.yaml`: an `async` transport on `%env(MESSENGER_TRANSPORT_DSN)%` (`doctrine://default?auto_setup=false`) with a retry strategy (3 retries, 1s delay, ×2 backoff) and a `failed` dead-letter transport (`doctrine://default?queue_name=failed`); `when@test` swaps `async` to `sync://` so jobs run inline and existing email assertions (`NotificationTest`, `NotificationTriggersTest`, `Invite*`, `Password*`, …) pass without a worker. The migration also installs the LISTEN/NOTIFY trigger (`notify_messenger_messages`) so the worker wakes on insert instead of polling. **All outbound email is async**: `Symfony\Component\Mailer\Messenger\SendEmailMessage` is routed to `async`, so every `MailerInterface::send()` (notifications, invites, password reset, 2FA, email-change, waitlist, digest/reminder crons) enqueues a delivery job — no per-mailer code. `NotificationDispatcher::sendEmail()` keeps its preference/quiet-hour gates then calls `$mailer->send()` (which is now the enqueue); do gating before send so only intended emails hit the queue. For a custom (non-email) job, add a message DTO + an `#[AsMessageHandler]` class under `api/src/Message/` + `api/src/MessageHandler/`, route it in `messenger.yaml`, and `MessageBusInterface::dispatch` it (see the "Adding a new job" guide in the doc). Dev worker = the `worker` service in `compose.yaml`/`compose.override.yaml`; prod = the `*-worker` Helm Deployment (`helm/api-platform/templates/worker-deployment.yaml`, gated on `worker.enabled`). See `docs/developer/job-queue.md`. **Recurring jobs run through symfony/scheduler on the same worker** (`messenger:consume async scheduler_default` — no system cron): `App\Scheduler\MainScheduleProvider` (`#[AsSchedule]`, stateful via cache.app + lock, `processOnlyLastMissedRun`) fires `App\Message\DispatchTaskReminders` every 5 min, `App\Message\DispatchNotificationDigest` hourly at :55 / daily at 08:00 UTC, and `App\Message\RunBackup` nightly at 02:00 UTC; the handlers delegate to `App\Service\TaskReminderDispatcher` / `NotificationDigestDispatcher` / `BackupRunner`, which also back the `app:tasks:reminders:dispatch`, `app:notifications:dispatch-digest`, and `app:backup:run` console commands for manual runs. Backups (`BackupRunner`): pg_dump over the network (postgresql-client in the api image) + tar of media, written to `./backups` (host bind on the worker), newest-5 retention via `app.backup_max_backups`; `scripts/deploy.sh` runs the same command pre-deploy in a one-off container of the incoming image. To add a recurring job: message + handler as above (no routing needed) + a `RecurringMessage` in `MainScheduleProvider`. The scheduler transport needs no `when@test` override — nothing consumes it in tests.
- **Analytics (self-hosted Umami)**: cookieless, privacy-first analytics via the `umami` compose service (`ghcr.io/umami-software/umami:postgresql-latest`, behind the `analytics` compose profile so CI/dev `up` skip it; `scripts/deploy.sh` exports `COMPOSE_PROFILES=analytics` so prod always runs it). Umami uses its own `umami` database on the shared Postgres (ensured idempotently by deploy.sh in prod; locally `docker compose exec database createdb -U app umami` once) and migrates itself on boot. Caddy proxies exactly two first-party paths — `/umami/script.js` + `/umami/api/send` — to `umami:3000`; the dashboard is served on its own hostname via a second Caddyfile site block (`UMAMI_SERVER_NAME`, prod `analytics.<domain>` + DNS A record; dev default `analytics.localhost`), with the loopback-published `127.0.0.1:${UMAMI_PORT:-3001}` kept as an SSH-tunnel fallback. PWA: `pwa/lib/analytics.ts` exposes `trackEvent(name, data?)` (no-ops when the tracker is absent); `_app.tsx` injects the tracker `<Script>` only when `NEXT_PUBLIC_UMAMI_WEBSITE_ID` is set (committed in `pwa/.env.production` after first-run dashboard setup — the ID is public; unset = analytics fully off, the dev/test default). Auto pageviews + a small kebab-case event catalog (`signup`, `task-create`, `project-create`, `page-create`, `discussion-create`, `comment-create`, `space-create`, `group-create`) — payloads stay coarse, never user content. See `docs/developer/analytics.md`.
- **Usage tracking (per-user cost estimation)**: Per-user accounting of four cost drivers — API calls, MCP calls, disk bytes, and a logical DB-size estimate — designed to keep all writes off the request latency path. Two tables (`Version20260611120000`): `user_usage_counter` (live counters bucketed per `(user, UTC day, metric)`, where `metric ∈ {api_call, mcp_call}`) and `user_usage_snapshot` (the nightly rollup queried for pricing — one row per `(user, captured_on)` with `disk_bytes` / `db_bytes_est` / `api_calls` / `mcp_calls`). **Counting is cheap + off-path**: `App\Service\UsageRecorder` increments a counter with a single `INSERT … ON CONFLICT DO UPDATE SET count = count + 1` UPSERT (so high-frequency events never spawn one row each), and swallows its own errors so accounting can never break the request it measures. API calls are counted by `App\EventListener\UsageTrackingListener` — it resolves the authenticated user at `kernel.request` (priority 0, after the firewall) and stashes it on the request, then increments at **`kernel.terminate`** (after the response is flushed), so the bookkeeping adds zero perceived latency; `/mcp` is skipped here. MCP calls are counted at the tool-dispatch chokepoint in `McpController` (right after `$tool->invoke()` returns) — per-tool, not per-envelope, and not double-counted as an API call. **Sizes are sampled nightly, never live**: `App\Service\UsageSnapshotBuilder` (cron `15 3 * * *` UTC via `App\Message\CaptureUsageSnapshot` on `MainScheduleProvider`; manual `app:usage:snapshot [--date=Y-m-d]`) computes per-user `disk_bytes = SUM(media_object.byte_size)` and a logical `db_bytes_est` = `SUM(octet_length(...))` over the big text columns each user owns across `task`/`project`/`page`/`comment`/`discussion` (owner cols: `owner_id`/`owner_id`/`created_by_id`/`author_id`/`author_id`) plus a per-row overhead constant — all set-based SQL, no N+1. `db_bytes_est` is a defensible logical proxy, **not** physical page bytes (exact per-user physical size isn't cheaply attributable in Postgres). The handler also prunes counter buckets past `app.usage_counter_retention_days` (default 90) once rolled up. Tunables: `app.usage_db_row_overhead_bytes` (default 512), `app.usage_counter_retention_days`. Read surface for pricing analysis: `app:usage:report [--days=30] [--limit=25]` prints a per-user table (latest disk/db in the window + summed calls). A `ROLE_ADMIN` HTTP endpoint is a natural follow-up. Tests: `App\Tests\Api\UsageTrackingTest`.

### Static analysis (PHPStan)
PHPStan runs against `api/src` and `api/tests` at **level 10** (max strictness in PHPStan 2.x) with `phpstan/phpstan-strict-rules` layered on top, as a required CI check. Config lives in [api/phpstan.dist.neon](api/phpstan.dist.neon); the baseline at [api/phpstan-baseline.neon](api/phpstan-baseline.neon) is intentionally minimal — a single wildcard entry that ignores `staticMethod.dynamicCall` (strict-rules wants `self::assertX()` everywhere, but `$this->assertX()` is PHPUnit-idiomatic and we keep it). Every other level-10 + strict-rules violation is cleared at the source. Regenerate after a cleanup pass with `docker compose run --rm phpstan analyse --generate-baseline=phpstan-baseline.neon`.

Patterns the codebase has converged on for surviving level 10:
- **Controllers reading JSON bodies**: `$payload = $request->toArray()` (typed `array<int|string, mixed>`) instead of `json_decode($request->getContent(), true)` (returns `mixed`). Pluck string fields through a private `stringField()` helper (see `TwoFactorController` / `PasswordController`) — `(string) ($data[$key] ?? '')` triggers `cast.string`.
- **Tests reading response bodies**: `$response->toArray()` (or `$response->toArray(false)` when the status may be non-2xx) plus inline `$x = $body['key']; $this->assertIsArray($x);` narrowing before any second-level offset access. The shared trait `App\Tests\Api\JsonBodyAssertions` packages this as `arrayField()` / `stringField()` / `intField()` / `boolField()` helpers — adopt it per-test as you touch them.
- **Nullable `?->equals()` chains in boolean contexts**: `true === $x?->getId()?->equals($y)` (strict-rules rejects bare `bool|null` as an `if`/`&&` operand).
- **`!preg_match(...)`**: write `1 !== preg_match(...)` — `preg_match` returns `int|false`, not bool.

Extensions wired up:
- `phpstan/phpstan-strict-rules` — ~30 semantic checks on top of level 10 (no short ternary, no `empty()`, explicit nullability in boolean contexts, etc.).
- `phpstan/phpstan-symfony` — service-id / config-resolver awareness via `var/cache/test/App_KernelTestDebugContainer.xml`, console application loaded from [api/tests/phpstan/console-application.php](api/tests/phpstan/console-application.php).
- `phpstan/phpstan-doctrine` — `getRepository()` / `QueryBuilder` / DQL typing. Needs an `objectManagerLoader` because our entities use the `doctrine.uuid_generator` Symfony service; see [api/tests/phpstan/object-manager.php](api/tests/phpstan/object-manager.php). Bootstrapping the test kernel requires the test cache to be warm (`bin/console -e test cache:warmup`) — CI does this for you.
- `phpstan/phpstan-phpunit` — `TestCase` assertion awareness so test-side dataset / mock typing stops tripping false positives.

Locally:
```bash
docker compose exec php bin/console -e test cache:warmup                            # one-time per repo refresh
docker compose run --rm phpstan analyse --memory-limit=4G                           # full analysis
docker compose run --rm phpstan analyse src/Filter --memory-limit=4G                # subset
docker compose run --rm phpstan analyse --generate-baseline=phpstan-baseline.neon   # after a cleanup pass
```
When you fix a batch of baselined errors, regenerate `phpstan-baseline.neon` in the same PR so the cleared patterns can't silently regress.

## Code Conventions

### PHP / API
- Follow [Symfony coding standards](https://symfony.com/doc/current/contributing/code/standards.html)
- Entities live in `api/src/Entity/` with API Platform attributes
- Use Doctrine ORM attributes for mapping
- Validate with Symfony Validator constraints
- Tests in `api/tests/Api/`

### TypeScript / PWA
- Components in `pwa/components/`; shadcn primitives live in `pwa/components/ui/` and should be the default for buttons, inputs, labels, alerts, cards, dropdowns, etc. Reach for raw Tailwind only when no primitive fits.
- Pages follow Next.js file-based routing in `pwa/pages/`.
- Imports prefer the `@/*` alias (`@/components/...`, `@/contexts/...`, `@/lib/...`) over deep relative paths.
- Use Tailwind CSS for styling. Reference design tokens via the shadcn variables (`bg-background`, `text-muted-foreground`, `border-input`, `text-destructive`, etc.) where possible. shadcn tokens use the canonical neutral baseColor (no brand override yet); brand cyan still lives in raw utilities (`bg-cyan-700`, `text-cyan-700`) on the navbar and link elements.
- Forms backed by Formik should use `FormikField` from `pwa/components/ui/formik-field.tsx` rather than hand-rolled `<Field>` + `<label>` + `<ErrorMessage>` blocks.
- Long-form description fields use `MarkdownEditor` for input and `MarkdownView` for rendering (both from `pwa/components/editor/`). Content is stored as markdown in the API's `TEXT` columns.
- **Developer component docs**: every reusable component in `pwa/components/ui/` and the shared pieces under `pwa/components/{editor,user,common}/` has a documentation page at `pwa/pages/dev/components/<slug>.tsx`, indexed by `pwa/components/dev/registry.ts`. When you add a new reusable component, rename one, change a prop's public shape, or add a new variant, update the matching docs page (live example + source snippet via the `<CodeBlock />` helper) and the registry entry in the same PR. The index lives at `/dev/components`.

### E2E Tests
- Shared helpers (auth + markdown editor) live in `e2e/tests/helpers.js` — prefer them over duplicating `registerAndSignIn` per spec.

### Git & Branching
- Two long-lived branches: `main` (development trunk, default branch, all PRs target it — always deployable) and `production` (what the server runs; updated only via a `main → production` promote PR)
- Merging a promote PR triggers the auto-deploy (`.github/workflows/deploy.yml`): images build in CI → GHCR, then `scripts/deploy.sh` on the server raises the maintenance page, takes a pre-deploy DB+media backup, swaps containers, health-checks, and lowers the page. Rollback = re-run the workflow with a previous `image_tag` SHA.
- Promote PRs use a **merge commit** (keeps `production` fast-forwardable); all other PRs squash-merge into `main`
- Create short-lived branches: `feature/`, `fix/`, `chore/`, `docs/`, `refactor/`
- See `docs/developer/branching-and-releases.md` for the full strategy

### Releases
- Date-based build numbers: `YYYY.MM.DD.N` (e.g., `2026.04.12.1`)
- Tag `main` when ready to release: `git tag 2026.04.12.1 && git push origin 2026.04.12.1`
- The **Changelog workflow** (`.github/workflows/changelog.yml`) auto-regenerates `CHANGELOG.md` and creates the GitHub Release via [git-cliff](https://github.com/orhun/git-cliff) on tag push; rules live in `cliff.toml`. Only `feat:`/`fix:`/`security:`/`perf:`/`refactor:` commits make the changelog — keep PR titles in conventional-commit form so they land in the right section.
