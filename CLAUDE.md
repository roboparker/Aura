# Madori - API Platform Project

## Overview

Madori is built on **API Platform**, a Symfony-based framework for building API-first applications. It uses a monorepo structure with three main components: a PHP API backend, a Next.js PWA frontend, and Playwright E2E tests.

## Project Structure

```
Aura/                 # repo/folder name is unchanged; the product is "Madori"
  api/                # Symfony/API Platform backend (PHP 8.4+)
  pwa/                # Next.js frontend (React/TypeScript)
  e2e/                # Playwright end-to-end tests
  helm/               # Kubernetes/Helm deployment charts
  docs/               # Project documentation
  .github/            # GitHub config (templates, workflows, policies)
  compose.yaml        # Docker Compose (dev environment)
  CHANGELOG.md        # Project changelog
  CODE_OF_CONDUCT.md  # Contributor code of conduct
  LICENSE             # GNU AGPL-3.0 (dual-licensed; commercial license available)
  CLA.md              # Contributor License Agreement (enables dual licensing)
```

## Tech Stack

### API (Backend)
- **Framework**: Symfony 7.4 with API Platform 4.x
- **PHP**: >= 8.4
- **Database**: PostgreSQL 16 (via Doctrine ORM)
- **Server**: FrankenPHP
- **Real-time**: Mercure (WebSocket-like push)
- **Testing**: PHPUnit
- **File storage**: league/flysystem-bundle (local adapter in dev, swap to S3 later via `api/config/packages/flysystem.yaml`). User-uploaded media lives under `/app/var/media/` in the container, served by Caddy at `/media/*`.
- **Image processing**: intervention/image (GD driver). See `api/src/Service/ImageUploadService.php`.
- **Media model**: `MediaObject` entity is the shared upload target for any domain entity that needs files. Used by `User.avatar`, `Task.attachments`, and `Space.attachments`. Uploads go through `POST /media-objects` (multipart), then entities link them via IRI. Sensitive bytes (kind=attachment) stream through the gated `GET /media-objects/{id}/download` endpoint, which re-checks owner / task-readability / space-membership before serving. Avatar bytes stay on the public `/media/...` Caddy route. Board-level attachments were collapsed up to the space — shared files now live at `space_attachment`, so every board + member in a space sees one shared file pool managed in the space detail's Files tab.
- **Spaces (#181, #185)**: Top-level container for content. Every user gets a non-deletable personal "Private" space at signup; additional shared spaces can be created and shared with users / `UserGroup`s. Roles are `admin` and `member` — admins manage members, edit metadata, and delete the space; members can read/write content and edit/delete only their own. `Space` and `SpaceMembership` (direct user, unique on space+user) live under `api/src/Entity/`; group-inherited membership now flows through `UserGroup.space` (each group is owned by exactly one space — the old `SpaceGroupMembership` join table was removed in #groups-space). PR 1 ([#181](https://github.com/roboparker/Aura/issues/181)) provisioned the entities, `/spaces` CRUD (admin-gated writes via `SpaceCreateProcessor` + entity-level `isAdmin(user)` security expressions), `SpaceAccessExtension` (EXISTS-subquery scoping mirroring `BoardAccessExtension`, with both direct and group-inherited membership), and the backfill that links every existing board / CFD to its creator's personal space. PR 2 ([#185](https://github.com/roboparker/Aura/issues/185)) is the behavior change: every access predicate, security expression, and board-membership check across the API now goes through space membership instead of the old `board.members` collection (which is dropped along with the `board_member` table; `Version20260507120000` backfills any pre-existing board members into `space_membership`). Helpers: `Space::hasMember(user)` / `isAdmin(user)` (UUID-based comparison so they survive `EntityManager::clear()`), `Space::getEffectiveUsers()` (deduped union of direct + group members), `Board::isAccessibleBy(user)` / `isSpaceAdmin(user)` / `getEffectiveMembers()`, `Task::isAccessibleBy(user)` (owner OR board's space includes user; standalone tasks remain owner-only). For DQL, `App\Doctrine\SpaceMembershipDql::userBelongsToBoardSpace($boardAlias)` returns the direct-or-via-group EXISTS fragment so the same boilerplate isn't copy-pasted across access extensions, the media-download controller, the task repository's reorder query, and the MCP tools. Access matrix: read/list any space member; create any space member (Board's `Post` accepts `space === null` so the existing PWA — which doesn't know about spaces yet — keeps working, the processor defaults it to the caller's personal space); edit any space member; delete = creator OR space admin (Board); CRUD on CustomFieldDefinition = space admin only. `CustomFieldDefinition` denormalises its parent board's space via `PrePersist` (`syncSpaceFromBoard`); `BoardSpaceDefaultListener` auto-fills `Board.space` for direct-EM persistence (tests, fixtures, future CLI). Personal-space invariant enforced at the DB by partial unique index `uniq_space_personal_per_user` on `space (created_by_id) WHERE is_personal = true`. The personal "Private" space is created in `UserPasswordHasherProcessor` post-persist so the membership row and space row land in the same flush as the user — a half-failed signup can't leave an orphan space behind. `POST /boards/{id}/members` is preserved as a thin shim that adds the resolved user to the board's space (role `member`) so the existing PWA keeps working until PR 4. Test helpers live in `App\Tests\Api\SpaceMembershipFixture` (`addBoardMember()` / `ensureSpaceMembership()`). PR 3 space invites ([#186](https://github.com/roboparker/Aura/issues/186)) is described under "Group + space invites" above. PR 4 ([#187](https://github.com/roboparker/Aura/issues/187)) shipped the active-space PWA UX: `pwa/contexts/ActiveSpaceContext.tsx` loads the user's space list from `GET /spaces`, exposes `{spaces, personalSpace, activeSpace, setActiveSpace, refresh, isActiveSpaceAdmin}`, and persists the choice in localStorage under `madori.activeSpaceId` (falls back to the personal space when the persisted choice is no longer accessible). `pwa/components/common/SpaceSwitcher.tsx` adds the dropdown next to the Madori wordmark with a Lock icon for personal spaces. `/spaces` (index) and `/spaces/{id}` (detail with members, invite-by-email form, pending invites list with revoke, and admin-only Delete) are the management surface; the navbar's "Manage spaces" link drops you into them. `/boards` listings append `?space={iri}` to scope to the active space; new boards POSTed from `/boards` pin themselves to the active space's IRI so a user in a shared space doesn't accidentally drop new work into their personal one. Owner-gating in `CustomFieldsManager` is replaced with `isSpaceAdmin` derived by looking up the board's parent space in the already-loaded space list (no extra fetch). Board detail page drops the per-board add-member form (members are space-level now) and surfaces a "Space" badge plus "Manage members in space" link. The `?space=` SearchFilter on Board lives behind the `space:read` group on the User entity (so the User row embedded inside `SpaceMembership.user` serializes with email/name/avatar fields the PWA needs).
- **Groups (space-owned, #groups-space)**: Named user-sets owned by a single `Space` (`UserGroup` entity exposed as `/groups` — API short name `Group`; the `UserGroup`/`user_group` prefix avoids the reserved SQL keyword `group` and the `Symfony\Component\Serializer\Attribute\Groups` clash). A group belongs to exactly one space (`UserGroup.space`, NOT NULL, onDelete CASCADE) and **every group member gains access to that space transitively** — a group is that space's access-granting "team". **Any member of the group's space** can create / edit / delete / manage it (consistent with tags & custom fields); there is no per-group owner, no ownership transfer, and delete is not step-up protected. `UserGroupAccessExtension` scopes listings to groups whose owning space the caller belongs to (reuses `SpaceMembershipDql::userBelongsToBoardSpace($rootAlias)` since the root alias holds `.space`); non-member item lookups return 404. **Membership is a first-class join entity** (`UserGroupMembership`, table `user_group_membership`, unique on `(user_group_id, user_id)`) carrying a `joinedAt` per member — there is no `role` column and no owner, so every member is equal. `UserGroup` helpers `getMembers()` (derived `Collection<User>` for the call sites that count/iterate members — `Space::hasMember`/`getEffectiveUsers`, invite flows, the membership DQL fragments which join `...g.memberships m ... m.user = :user`), `hasMember()` (UUID-based, survives `EM::clear()`), `addMember()`/`removeMember()`. Extra fields: `color` (palette-validated, nullable → UI falls back to the space color via `resolveGroupColor`), `slug` (stable `g-`-prefixed handle generated once from the title by `UserGroupOwnerProcessor`, globally unique, read-only — direct-persist sites like fixtures/tests must `setSlug()` themselves), and `updatedAt` (Gedmo Timestampable). `space` is in `group:write` (set on create, treated as immutable after; creation gated by a `securityPostDenormalize` checking `object.getSpace().hasMember(user)`). `getSpaceSummary()` (a `group:read` getter) emits `{id,name,color,isPersonal}` of the owning space for the detail "Belongs to" card + color fallback. **Endpoints** (all in `UserGroupMemberController` unless noted, gated on space membership via `canManage`): `POST /groups/{id}/members` (add-by-email — existing user → direct membership, unknown → invite); `DELETE /groups/{id}/members/{userId}`; `POST /groups/{id}/leave` (any member self-removal; a group may end up empty). `DELETE /groups/{id}` is a plain space-member delete (no step-up). `GET|DELETE /groups/{id}/invites[/{id}]` + `POST /groups/{id}/invites/{id}/resend` (rotate token + re-send) in `UserInviteController`. **Group→space access**: the old `SpaceGroupMembership` join table is **gone** — `Space::hasMember()`/`getEffectiveUsers()` and the group branch of `SpaceMembershipDql` (+ its inlined copies in `TaskOwnerExtension`, `CommentAccessExtension`, `SpaceAccessExtension`, `MediaObjectDownloadController`, `ListSpacesTool`, `DownloadFileTool`, `TaskRepository`) walk `UserGroup` directly via its `space` FK; `Space::getGroupsCount()` (`space:read`) backs the visibility-flip warning, and flipping a shared space → private deletes the space's groups (`SpaceUpdateProcessor`). Account deletion no longer transfers groups — `UserGroupMembership.user` CASCADE drops the deleted user from rosters, and a group in a removed space dies with it. `Version20260627120000` backfills `user_group.space_id` (from the prior attachment, else the owner's personal space) then drops `space_group_membership` + `user_group.owner_id` (destructive — multi-space groups keep one space). **PWA**: groups are managed on the space **Users page** (`/spaces/{id}/users`, admin-only — alongside the space's direct members + pending invites), reached from the **sidebar Settings** section (General · Users · Roles · API keys — admin-scoped; Tags and Custom fields are now top-level sidebar items, and the active-space switcher sits at the top of the full-height left sidebar). The Users page lists the space's groups (each links to the group detail) with a "New group" button; the standalone `/groups` index was folded in and now redirects to the active space's Users page. `/groups/new` (POSTs `space: activeSpace`; name + description + `ColorSwatchPicker` + `EmailChipInput`) and `/groups/{id}` detail (edit / members / add-member / pending-invites / danger-zone, "Belongs to {space}" card; no owner badge, transfer, or "your access" card) remain. Shared bits: `GroupTile` (mirrors `SpaceTile`), `resolveGroupColor` (falls back to the space color) in `pwa/lib/avatarPalette.ts`, types in `pwa/lib/groupTypes.ts`; `DeleteGroupDialog` is a type-to-confirm with no step-up; `TransferOwnershipDialog` was removed. Tests: `App\Tests\Api\UserGroupTest`, `UserGroupMemberEdgeTest`.
- **Per-space custom roles (#space-roles)**: space admins define named **roles** (a per-content-type CRUD permission matrix) and assign one or more to each direct member to *restrict* what they can do — **enforced** server-side, in MCP, and gated in the PWA. Rules (**Model A**): admins always have everything; owners/authors can always act on their own content; a member with **zero roles is unrestricted** (back-compat, so no migration/backfill); a member's effective permissions are the **union** of their roles, and a role can **grant beyond the old baseline** (e.g. delete others' content); group-inherited members keep full access in v1. `App\Security\Permission\SpacePermission` is the vocabulary (`boards, tasks, pages, comments, custom_fields, tags, groups, files, api_keys` × `create, read, update, delete`; riders: task sections→boards, task relationships→tasks). `api_keys` is **admin-reserved by default** — it's excluded from the built-in Member (`fullMatrix`) and Guest (`guestMatrix`) presets, so a non-admin only gains it through an explicitly-assigned custom role; `SpacePermissionResolver::canByExplicitGrant()` gates it (space admins always, plus members whose assigned roles grant it — never the "zero-roles = unrestricted" fallback). `App\Entity\SpaceRole` (table `space_role`, per-space `name`/`color`/`permissions` JSON matrix) is an ApiResource: member-read scoped by `SpaceRoleAccessExtension`, space-admin write. `SpaceMembership.roles` is a `ManyToMany(SpaceRole)` (join `space_membership_role`, `space:read`); assigned via `PATCH /spaces/{id}/members/{membershipId}` (`SpaceMemberController` accepts `roles: [iri]`). **Enforcement** (`App\Security\Permission\`): `SpacePermissionResolver` (`can(user, space, category, action)` + `readDeniedSpaceIds()` deny-list + `effectiveMatrix()`) is the single source of truth; `SpacePermissionVoter` exposes `is_granted('space.<category>.<action>', object)` (resolves each subject's space) which every content entity's `security:` expression ANDs onto its membership branch (keeping `ROLE_ADMIN` + owner/author bypasses; **comment edit stays author-only**, not role-grantable). Collection reads are filtered by the deny-list in the access extensions (empty list = no-op, so unrestricted users are byte-for-byte unchanged) via a `getPermissionCategory()` hook on `AbstractSpaceAccessExtension` + inline in `TaskOwnerExtension`/`UserGroupAccessExtension`. MCP honors roles through `McpAuthorization` (layers the resolver). Migration `Version20260628214813` adds the two tables (no backfill). **PWA**: admin-only **Roles** page (`pwa/pages/spaces/[id]/roles.tsx`, sidebar Settings → Roles) with `RolePermissionMatrix` (`pwa/components/spaces/RolePermissionMatrix.tsx` — per-row, per-column, and master All/None toggles) + `ColorSwatchPicker`; per-member `MemberRoles` dropdown on the Users page; `ActiveSpaceContext.can(category, action)` (fed by `GET /spaces/{id}/my-permissions` → `MySpacePermissionsController`) gates create/edit buttons (server stays the enforcer). Types in `pwa/lib/roleTypes.ts`. **Built-in roles**: each space seeds a non-deletable, editable **Member** role (the implicit default for members with no assigned role — full access until tightened) + **Guest** (read content + comment), via `App\Service\SpaceRoleSeeder` (on signup + shared-space create) and a backfill migration; the resolver falls back to the Member role for unassigned members (`SpaceRole.builtinKey`). **Space-scoped API keys** (`api/src/Controller/SpaceApiKeyController.php`, `POST|GET|DELETE /spaces/{id}/api-keys`, gated by the `api_keys` permission — space admins by default, or a member granted it via a role): an `ApiToken` with a non-null `space` + assigned `roles` (M2M) is a Bearer key **confined to that space** and narrowed to the union of its roles (no role ⇒ inert; personal tokens with `space === null` are unchanged). A scoped key authenticates as its creator (so membership checks pass) but `App\EventListener\SpaceKeyAccessListener` gates it by role-CRUD per request *before* the entity expressions (so the creator's owner/admin bypasses can't leak) and the access extensions + `App\Security\Permission\ActorContext`/`SpacePermissionResolver` confine its rows/items to the key's space; scoped keys are rejected over MCP in v1. PWA: `/spaces/[id]/api-keys` page (role multi-select + one-shot plaintext reveal), reachable by anyone with `api_keys` read (admins included) via the sidebar Settings link and gated per-action by `ActiveSpaceContext.can('api_keys', …)`. Tests: `App\Tests\Api\SpaceRoleTest`, `SpacePermissionEnforcementTest`, `SpaceApiKeyTest`.
- **Group + space invites**: One `UserInvite` per email (unique) collects every pending attachment for that address: `GroupInvite` rows for groups, `SpaceInvite` rows for spaces (#186). Tokens are sha256-hashed like `PasswordResetToken`; the plaintext is only ever in the email. Add-by-email: `POST /groups/{id}/members` (any member of the group's space) and `POST /spaces/{id}/members` (admin-only) — each branches on whether the email matches an existing user (direct membership) vs unknown (upsert + invite). `App\Service\InviteMailer` renders the signup-link email with the union of every group + space currently attached, qualified as `group "X"` / `space "Y"` so a recipient invited to both gets one coherent message; token rotation on every send keeps the most recent email authoritative. Public lookup at `GET /invites/{token}` returns `status` (`'pending' | 'expired' | 'accepted'`), `email`, `expiresAt`, and an `inviter` chip (`{name, email, initials, color}`). Pending responses also include `groups[]` (each with `memberCount`) and `spaces[]` (each with `role`). The PWA's `InviteSignup` component (`pwa/components/auth/InviteSignup.tsx`) branches on the status — pending renders the accept form with the invite-context list above it, `expired` shows the "ask the sender for a new link" card with a mailto fallback, `accepted` shows the "this invite was already used" card, and a signed-in viewer whose email doesn't match the invite email gets the mismatch screen. 404 still means an unknown token. Invite management lives at `GET|DELETE /groups/{id}/invites[/...]` (any member of the group's space) and `GET|DELETE /spaces/{id}/invites[/...]` (space admin); revoking the last attachment on a `UserInvite` removes the parent so a token can't redeem to nothing. When the invitee signs up via the link (`POST /users` with `inviteToken`), `UserPasswordHasherProcessor` walks both `groupInvites` and `spaceInvites` and attaches the new user — provided the signup email matches the invite email.
- **Custom fields (#227, space-owned #custom-fields-space)**: Space-owned schema (`CustomFieldDefinition.space`, NOT NULL); boards opt in to the fields they show via a `Board.customFieldDefinitions` many-to-many (`board_custom_field_definition` join table), so each board's task list shows only its chosen subset. Storage shape is `(kind, subtype, config, footer, nullable)` — `kind` is the top-level family (`boolean`/`text`/`numeric`/`date`/`select`/`reference`), `subtype` the specialisation (e.g. `numeric.money`, `select.multi`, `reference.user`), `config` the per-kind JSON payload (options, min/max, currency, multi, …), `footer` an optional `{kind, label?}` aggregation descriptor, `nullable` the inverse of the legacy `required` flag (kept as a denormalised mirror column for now). Per-kind editor + validator logic lives in `api/src/CustomField/Type/` behind `CustomFieldTypeInterface`: each (kind, subtype) is one strategy class, auto-tagged `app.custom_field_type` and resolved through `CustomFieldTypeRegistry`. Adding a new kind is a one-class drop on both sides of the wire (PHP strategy + matching TS entry in `pwa/components/custom-fields/kind-editors.tsx`). Definitions are managed by **any member of the field's space** (CRUD at `/custom_field_definitions`, `?space=`-filterable; reads scoped via `CustomFieldDefinitionAccessExtension`). The PWA mounts `CustomFieldsManager` (`pwa/components/custom-fields/`) on the space-level `/custom-fields` page (sidebar Settings) and on the board's Settings → Custom fields tab; the board tab also renders `BoardCustomFieldPicker` (tick which of the space's fields show on this board, PATCHing `Board.customFieldDefinitions`). The standalone `/boards/{id}/custom-fields` page was removed. In the manager, kind/subtype dropdowns swap in the matching config editor (currency for money, min/max for numeric/date, structured options list for select, length + regex for text). Per-task values live on `CustomFieldValue`, embedded as `Task.customFieldValues` (`{definition, value}` pairs) — clients write the whole array via the Task `task:write` group and orphanRemoval reaps anything dropped. The `(task_id, definition_id)` unique constraint is `DEFERRABLE INITIALLY DEFERRED` so PATCH's delete-then-insert collapses cleanly. `ValidCustomFieldValues` (class-level constraint on Task) dispatches through the strategy registry — top-level invariants (space-scope, no dup definition, required-when-not-nullable) stay in the validator; per-value shape rules live on each strategy. Companion `ValidCustomFieldDefinition` (class-level on CFD) dispatches `validateConfig()` + checks `footer.kind` against the strategy's supported aggregations. Money values are `{amount: int-minor-units, currency: ISO-4217}` with the currency pinned on the field's `config`; reference values are IRIs scoped to the field's space (`reference.user` walks `space.getEffectiveUsers()`; the rest compare `target.space === field.space`). The FTS projection on `custom_field_value.value_search` is written by `CustomFieldValueSearchSubscriber` calling `strategy.searchText()` on persist/update so references serialize their target's display label and money emits `<amount> <currency>` — `search_vector` then derives from `value_search` via STORED generated column. Legacy `CustomFieldDefinition::setType()` / `setOptions()` remain as internal entity helpers (no `#[Groups]`, off the wire) so test seeders and the migration backfill still speak the old labels; the canonical API contract is `{kind, subtype, config, nullable}`. Reference subtypes are `user`/`task`/`board`/`page` — `reference.board` (`BoardReferenceStrategy`) scopes to boards in the field's space like the others. **PWA redesign**: `CustomFieldsManager` renders the schema as a drag-to-reorder table (NAME · KIND · REQUIRED · FOOTER) backed by `@dnd-kit` (the KIND cell is a plain rounded badge — no color dot; the space-level `/custom-fields` table sits on a `bg-card` surface); create/edit/delete happens in a right-side `CustomFieldSheet` drawer (our `ui/sheet.tsx`) with rich per-kind editors in `kind-editors.tsx` (searchable currency `Combobox` + derived decimals + live money preview, live regex pattern-check for text/url, `Calendar` date-range bounds, `@dnd-kit` select options with per-option color swatches + usage counts, reference target-type cards). Required + multi are `ui/switch.tsx` toggles (base-ui Switch); footer aggregation is a `NONE|COUNT|SUM|AVG|MIN|MAX` pill row + label override. Supporting endpoints (all space-access scoped, 404 for outsiders): `POST /boards/{id}/custom_field_definitions/reorder` (any space member, renumbers `position` contiguously — `CustomFieldDefinitionReorderController`), `GET /boards/{id}/custom_field_stats` (`{total, stats:[{definition, filled}]}` — the standalone FILLED column was dropped; the counts now feed the per-field value count in the edit drawer), `GET /custom_field_definitions/{id}/option_stats` (`{options:[{key,label,count}]}` per-option usage), and `GET /boards/{id}/custom_field_definitions/activity` (board-scoped change log — `CustomFieldDefinition` is Gedmo `Loggable`, served via `CustomFieldDefinitionActivityController` + the shared `ActivityFeedSerializer`, surfaced in the `CustomFieldChangeLog` drawer). The static ISO-4217 list for the money picker lives in `pwa/lib/currencies.ts`; decimal places are derived from the currency, not stored.
- **Custom-field footer aggregation (#227)**: `GET /boards/{id}/custom_field_footers` returns one row per CFD that has a `footer.kind` configured, with the aggregation computed over the filtered task list. Endpoint honours `?search=`, `?status=`, `?overdue=`, `?dueDate[before|after|strictly_*]` (Task collection filter subset). Numeric int/float/money push through SQL (`(value #>> '{...}')::numeric` + `SUM/AVG/MIN/MAX`), date kinds use lex MIN/MAX on the JSON-extracted text, every kind supports `count` of non-null values. Money returns `{amount, currency}` so the PWA's `CustomFieldFooterRow` (under the board task list) can format with `Intl.NumberFormat`. Multi-value sum/avg/min/max returns null in v1 — JSON array unroll is out of scope.

- **Task recurrence + reminders**: `Task.recurrenceRule` is a JSON object `{frequency: daily|weekly|monthly|yearly, interval: int≥1, byDay?: [MO..SU], monthlyMode?: day|weekday, bySetPos?: int (1..5|-1, monthly-weekday only), ends?: {type: until, until: YYYY-MM-DD} | {type: count, count: int≥1}}` (no `ends` = infinite; `count` is total occurrences **including** the anchor). `Task.reminders` is a JSON array (max 10) of `{type: relative, value: int≥0, unit: minutes|hours|days, repeat: bool}` (relative requires a `dueDate`) or `{type: absolute, at: ISO-8601, repeat: bool}` (no due date needed); `repeat: true` fires daily until the task completes. Recurrence + relative reminders both require `dueDate`. Validation is class-level on `Task` via `ValidRecurrence`/`ValidRecurrenceValidator` (byDay/monthly-weekday/ends shape, recurrence-needs-due) and `ValidReminders`/`ValidRemindersValidator` (≤10, no duplicate canonical keys, relative-needs-due); `Task::setReminders([])` normalises empty → null. - **2FA (TOTP)**: opt-in per user, powered by [SchebTwoFactorBundle](https://symfony.com/bundles/SchebTwoFactorBundle/current/index.html) (`scheb/2fa-bundle` + `scheb/2fa-totp` + `scheb/2fa-backup-code`). The `User` entity implements `TwoFactorInterface` and `BackupCodeInterface`. The TOTP secret is stored encrypted (sodium secretbox via `App\Service\TwoFactorSecretCipher`, key derived from `APP_SECRET`) and decrypted into a transient cache by `App\EventListener\UserTotpCipherInjector` on Doctrine `postLoad`. Setup/verify/disable/regenerate-codes/reveal-codes endpoints live at `/me/2fa/*` (controller: `TwoFactorController`); the login challenge piggy-backs on the bundle's firewall listener at `/auth/2fa-check`, with JSON request/response handlers in `App\Security\TwoFactorJsonHandler`. Verify-code attempts are throttled per user via the `two_factor_verify` rate limiter (5/min). Recovery codes are stored as sha256 hashes (one-time use; consumed code removed from the JSON list). **Step-up for sensitive self-service actions** (disable 2FA, regenerate or reveal recovery codes, change password) routes through `App\Service\SensitiveActionVerifier`: when 2FA is enabled the body must carry a `totpCode` (validated through the same per-user `two_factor_verify` limiter as login); when 2FA is off it falls back to `currentPassword`. A stolen cookie can't silently rotate the password or disarm 2FA without the authenticator device. - **Usage tracking (per-user cost estimation)**: Per-user accounting of four cost drivers — API calls, MCP calls, disk bytes, and a logical DB-size estimate — designed to keep all writes off the request latency path. Two tables (`Version20260611120000`): `user_usage_counter` (live counters bucketed per `(user, UTC day, metric)`, where `metric ∈ {api_call, mcp_call}`) and `user_usage_snapshot` (the nightly rollup queried for pricing — one row per `(user, captured_on)` with `disk_bytes` / `db_bytes_est` / `api_calls` / `mcp_calls`). **Counting is cheap + off-path**: `App\Service\UsageRecorder` increments a counter with a single `INSERT … ON CONFLICT DO UPDATE SET count = count + 1` UPSERT (so high-frequency events never spawn one row each), and swallows its own errors so accounting can never break the request it measures. API calls are counted by `App\EventListener\UsageTrackingListener` — it resolves the authenticated user at `kernel.request` (priority 0, after the firewall) and stashes it on the request, then increments at **`kernel.terminate`** (after the response is flushed), so the bookkeeping adds zero perceived latency; `/mcp` is skipped here. - **Task sections + board view (#496)**: Board organisation for board tasks. `TaskSection` (per-board `title` + `position`, table `task_section`) at `/task_sections` — any space member CRUDs (security via `object.getBoard().isAccessibleBy(user)`), collection scoped by `TaskSectionAccessExtension`. `Task.section` is a **nullable** FK (`onDelete: SET NULL`); null = the implicit default "In progress" group, so existing tasks need no backfill and deleting a section drops its tasks back to the default. - **Timeline / Gantt view (#timeline)**: A board-level Gantt, opt-in per board via a single **`Board.timelineEnabled`** toggle. Each task's bar runs from the canonical global **"Start date"** field to its native **`dueDate`** (the deadline the rest of the app already uses); a task with a due date but no start renders as a **milestone diamond**, one with neither is listed as "unscheduled" below the chart. **The start field is one seeded, system-owned global custom field** — `GlobalCustomFieldDefinition` gains a nullable-unique **`systemKey`** column (the canonical row carries `GlobalCustomFieldDefinition::SYSTEM_TIMELINE_START = 'timeline_start'`, seeded in `Version20260725030744`); a non-null `systemKey` blocks Delete (`security` expr on the op) and a class-level `Assert\Callback` keeps its kind = date. `GlobalCustomFieldDefinitionRepository::findTimelineStartField()` resolves it by key. The **field's presence on a board is derived from the toggle**: `App\State\BoardTimelineProcessor` (the board `Patch` processor) attaches the canonical field to `board.globalCustomFieldDefinitions` whenever `timelineEnabled` is true and re-adds it if a request tries to drop it — so turning Timeline off is the only way to remove it. (No validator: the processor is the write step and runs *after* validation, which is exactly why the invariant lives there — the field is legitimately absent at validation time right after the toggle flips on.) **`GET /boards/{id}/dependencies`** (`BoardTimelineController`) returns the `required` **and** `parent` edges among the board's own tasks in one query (`TaskRelationshipRepository::findEdgesInBoard`, source→target = predecessor→dependent / parent→child) — `required` draws the arrows, `parent` drives row nesting; cross-board edges dropped. **`GET /spaces/{id}/dependencies`** is the space-scoped sibling for the cross-board `/timeline` page (`findEdgesInSpace`) — it *keeps* board-spanning links since both ends have rows there, but both must sit inside the space. Bars need no endpoint: the board page already loads tasks with their custom-field values, so start (the canonical field's value) + end (`dueDate`) resolve client-side. **PWA**: `pwa/components/boards/BoardTimeline.tsx` (generic over the task type) — section-grouped rows, day/week/month zoom, today line, SVG dependency arrows, pointer-drag to move (shifts both dates) or resize edges (start via the field value, end via `dueDate`); mounts as a **Timeline** tab on `pwa/pages/boards/[id].tsx` next to List/Board/Calendar (empty state until enabled). Settings has an **Enable Timeline** `Switch` (PATCHes `timelineEnabled`); the PWA resolves the canonical field by `systemKey === 'timeline_start'` (exposed via `TIMELINE_START_SYSTEM_KEY` in `pwa/components/custom-fields/types.ts`). **Read-only schedule analysis** lives in `pwa/lib/timelineAnalysis.ts`: the **critical path** (longest-span `required` chain — memoised DFS longest-path with a `visiting` guard, since `required` has no server-side cycle check unlike `parent`; rendered amber *and* ringed so it survives colour-blindness; a lone task is never "critical") and **violated dependencies** (a dependent starting on/before its prerequisite ends → red arrow + legend count). **Auto-scheduling was declined** — one drag could silently rewrite many people's due dates with no obvious undo, so the chart surfaces problems and leaves the fix to a human. **Subtask nesting**: `parent` edges indent children under their parent (`nestByParent`; a parent that's off-chart is treated as a root, which is what keeps board-scoped charts safe). **Cross-board page** `pwa/pages/timeline.tsx` (`/timeline`, sidebar under Calendar) charts every timeline-enabled board in the active space, one group per board (same component, `groupBy` swapped from section to board) and `readOnly` — rescheduling stays on the owning board's tab where the config lives. Tests: `App\Tests\Api\BoardTimelineTest`, `pwa/lib/timelineAnalysis.test.ts`, `e2e/tests/boards.spec.js`.

- **Task relationships (#497)**: Directed links between tasks. `TaskRelationship` (`source`/`target` Task FKs + `type`, table `task_relationship`, unique on `(source, target, type)`) at `/task_relationships`. `type ∈ {parent, required, related, duplicate}`; one row stores the relationship source→target and the label is derived per viewing side (`TaskRelationship::labelFor()` — `parent` reads "parent of" from the source, "child of" from the target; `required` → "required for"/"required by"; `duplicate` → "duplicate of"/"duplicated by"; `related` is symmetric). `ValidTaskRelationship` rejects self-links and a same-type duplicate in **either** direction (so `A parent-of B` blocks the reverse `B parent-of A`, while a *different* type between the same pair is allowed). The resource exposes only Post/Get/Delete (security gates on `source`/`target` `isAccessibleBy`); reads come through `GET /tasks/{id}/relationships` (`TaskRelationshipController`), which returns each link from the task's viewpoint with the resolved label + the other task's summary. PWA: a **Relationships** section in the task drawer (`pwa/components/tasks/TaskRelationshipsPanel.tsx`) — list with labels, add form (directional type picker + task search), per-row remove.
- **Subtasks (#497 follow-up)**: nested subtask UX built **on the `parent` relationship** (no new schema) — a subtask is a task that's the *target* of a `parent` link. `ValidTaskRelationshipValidator` adds two invariants for `parent` links only: **single-parent** (a task is the target of at most one `parent` link — `TaskRelationshipRepository::findParentLinkOf()`) and **no cycles** (a BFS down the child tree via `findChildLinksOf()` rejects making a task the subtask of its own descendant; catches multi-hop loops the direct-pair duplicate check misses). `GET /tasks/{id}/subtasks` (`TaskRelationshipController::subtasks`) returns the ordered children + a `{total, completed}` rollup + the task's own `parent` link (so the drawer shows "part of <parent>" without a second fetch). Completion is **never automatic** — a parent isn't auto-completed or blocked by open children; the count is informational (per the product decision). PWA: `pwa/components/tasks/SubtasksPanel.tsx` in the drawer above Relationships — progress bar + `N/M`, per-child complete checkbox (PATCH the child) + unlink (DELETE the relationship; the child task survives), inline "add subtask" that creates a task on the parent's board then links it (a fresh task can't trip either invariant). **Rollup on rows**: task *collections* carry `subtaskProgress` (`{total, completed}`) attached by `App\State\TaskSubtaskProgressProvider` — it decorates `TaskSearchProvenanceProvider` (which decorates the stock collection provider, preserving access scoping/filters/pagination) and adds exactly one batched query per page via `TaskRelationshipRepository::subtaskProgressFor()`. Collection-only by design (the drawer already calls `/subtasks`, so a per-item query would buy nothing); childless tasks keep the zeroed default so clients never null-check. `pwa/components/tasks/SubtaskProgressBadge.tsx` renders the "2/5" on board list rows + Kanban cards and hides itself at `total: 0` (testid `subtask-progress-badge`, distinct from SubtasksPanel's own `subtask-progress`). **MCP**: `get_task` returns the rollup as `subtasks`; the three collection tools go through `McpEntitySerializer::tasks()` (plural), which batches the same call — mapping over the singular `task()` would reintroduce the N+1, which is why the plural exists. Tests: `App\Tests\Api\TaskRelationshipTest::testSubtaskInvariantsAndProgressRollup` + `::testCollectionCarriesSubtaskProgress`, `McpTest::testGetTaskCarriesTheSubtaskRollup`, `e2e/tests/boards.spec.js`.
- **Web Push frontend (#100)**: Completes the push pipeline begun by the backend `PushSubscription` / `App\Push\WebPushSender`. `pwa/public/sw.js` (service worker, registered from `_app.tsx`) renders a `PushPayload` (`{title, body, url, tag}`) as a desktop notification and focuses/opens the target URL on click. `pwa/lib/push.ts` `enablePush()` runs the opt-in: request permission → `PushManager.subscribe()` with the VAPID public key → `POST /me/push-subscriptions`. `pushNotificationsEnabled` defaults to **true**; `EnablePushPrompt` (`pwa/components/notifications/EnablePushPrompt.tsx`) shows a small amber warning in the `RemindersEditor` when a task has reminders but the browser isn't granted, with an inline "Turn on" — its "Not now" never disables the account-level setting (public-computer safe). **VAPID keys**: the public key is committed in `pwa/.env.production` as `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (shipped to browsers — not secret; baked into the PWA at CI build); the API reads `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` via `%env(default::VAPID_*)%` (`WebPushSender` no-ops with a warning when blank). ### Static analysis (PHPStan)
PHPStan runs against `api/src` and `api/tests` at **level 10** (max strictness in PHPStan 2.x) with `phpstan/phpstan-strict-rules` layered on top, as a required CI check. Config lives in [api/phpstan.dist.neon](api/phpstan.dist.neon); the baseline at [api/phpstan-baseline.neon](api/phpstan-baseline.neon) is intentionally minimal — a single wildcard entry that ignores `staticMethod.dynamicCall` (strict-rules wants `self::assertX()` everywhere, but `$this->assertX()` is PHPUnit-idiomatic and we keep it). Every other level-10 + strict-rules violation is cleared at the source. Regenerate after a cleanup pass with `docker compose run --rm phpstan analyse --generate-baseline=phpstan-baseline.neon`.

Patterns the codebase has converged on for surviving level 10:
- **Controllers reading JSON bodies**: `$payload = $request->toArray()` (typed `array<int|string, mixed>`) instead of `json_decode($request->getContent(), true)` (returns `mixed`). Pluck string fields through a private `stringField()` helper (see `TwoFactorController` / `PasswordController`) — `(string) ($data[$key] ?? '')` triggers `cast.string`.
- **Tests reading response bodies**: `$response->toArray()` (or `$response->toArray(false)` when the status may be non-2xx) plus inline `$x = $body['key']; $this->assertIsArray($x);` narrowing before any second-level offset access. The shared trait `App\Tests\Api\JsonBodyAssertions` packages this as `arrayField()` / `stringField()` / `intField()` / `boolField()` helpers — adopt it per-test as you touch them.
- **Nullable `?->equals()` chains in boolean contexts**: `true === $x?->getId()?->equals($y)` (strict-rules rejects bare `bool|null` as an `if`/`&&` operand).
- **`!preg_match(...)`**: write `1 !== preg_match(...)` — `preg_match` returns `int|false`, not bool.

Extensions wired up:
- `phpstan/phpstan-strict-rules` — ~30 semantic checks on top of level 10 (no short ternary, no `empty()`, explicit nullability in boolean contexts, etc.).
- `phpstan/phpstan-symfony` — service-id / config-resolver awareness via `var/cache/test/App_KernelTestDebugContainer.xml`, console application loaded from [api/tests/phpstan/console-application.php](api/tests/phpstan/console-application.php).
- `phpstan/phpstan-doctrine` — `getRepository()` / `QueryBuilder` / DQL typing. Needs an `objectManagerLoader` because our entities use the `doctrine.uuid_generator` Symfony service; see [api/tests/phpstan/object-manager.php](api/tests/phpstan/object-manager.php). Bootstrapping the test kernel requires the test cache to be warm (`bin/console -e test cache:warmup`) — CI does this for you.
- `phpstan/phpstan-phpunit` — `TestCase` assertion awareness so test-side dataset / mock typing stops tripping false positives.

Locally:
```bash
docker compose exec php bin/console -e test cache:warmup                            # one-time per repo refresh
docker compose run --rm phpstan analyse --memory-limit=4G                           # full analysis
docker compose run --rm phpstan analyse src/Filter --memory-limit=4G                # subset
docker compose run --rm phpstan analyse --generate-baseline=phpstan-baseline.neon   # after a cleanup pass
```
When you fix a batch of baselined errors, regenerate `phpstan-baseline.neon` in the same PR so the cleared patterns can't silently regress.

## Code Conventions

### PHP / API
- Follow [Symfony coding standards](https://symfony.com/doc/current/contributing/code/standards.html)
- Entities live in `api/src/Entity/` with API Platform attributes
- Use Doctrine ORM attributes for mapping
- Validate with Symfony Validator constraints
- Tests in `api/tests/Api/`

### TypeScript / PWA
- Components in `pwa/components/`; shadcn primitives live in `pwa/components/ui/` and should be the default for buttons, inputs, labels, alerts, cards, dropdowns, etc. Reach for raw Tailwind only when no primitive fits.
- Pages follow Next.js file-based routing in `pwa/pages/`.
- Imports prefer the `@/*` alias (`@/components/...`, `@/contexts/...`, `@/lib/...`) over deep relative paths.
- Use Tailwind CSS for styling. Reference design tokens via the shadcn variables (`bg-background`, `text-muted-foreground`, `border-input`, `text-destructive`, etc.) where possible. shadcn tokens use the canonical neutral baseColor (no brand override yet); brand cyan still lives in raw utilities (`bg-cyan-700`, `text-cyan-700`) on the navbar and link elements.
- Forms backed by Formik should use `FormikField` from `pwa/components/ui/formik-field.tsx` rather than hand-rolled `<Field>` + `<label>` + `<ErrorMessage>` blocks.
- Long-form description fields use `MarkdownEditor` for input and `MarkdownView` for rendering (both from `pwa/components/editor/`). Content is stored as markdown in the API's `TEXT` columns.
- **Developer component docs**: every reusable component in `pwa/components/ui/` and the shared pieces under `pwa/components/{editor,user,common}/` has a documentation page at `pwa/pages/dev/components/<slug>.tsx`, indexed by `pwa/components/dev/registry.ts`. When you add a new reusable component, rename one, change a prop's public shape, or add a new variant, update the matching docs page (live example + source snippet via the `<CodeBlock />` helper) and the registry entry in the same PR. The index lives at `/dev/components`.

### E2E Tests
- Shared helpers (auth + markdown editor) live in `e2e/tests/helpers.js` — prefer them over duplicating `registerAndSignIn` per spec.

### Git & Branching
- Two long-lived branches: `main` (development trunk, default branch, all PRs target it — always deployable) and `production` (what the server runs; updated only via a `main → production` promote PR)
- Merging a promote PR triggers the auto-deploy (`.github/workflows/deploy.yml`): images build in CI → GHCR, then `scripts/deploy.sh` on the server raises the maintenance page, takes a pre-deploy DB+media backup, swaps containers, health-checks, and lowers the page. Rollback = re-run the workflow with a previous `image_tag` SHA.
- Promote PRs use a **merge commit** (keeps `production` fast-forwardable); all other PRs squash-merge into `main`
- Create short-lived branches: `feature/`, `fix/`, `chore/`, `docs/`, `refactor/`
- See `docs/developer/branching-and-releases.md` for the full strategy

### Releases
- Date-based build numbers: `YYYY.MM.DD.N` (e.g., `2026.04.12.1`)
- Tag `main` when ready to release: `git tag 2026.04.12.1 && git push origin 2026.04.12.1`
- The **Changelog workflow** (`.github/workflows/changelog.yml`) auto-regenerates `CHANGELOG.md` and creates the GitHub Release via [git-cliff](https://github.com/orhun/git-cliff) on tag push; rules live in `cliff.toml`. Only `feat:`/`fix:`/`security:`/`perf:`/`refactor:` commits make the changelog — keep PR titles in conventional-commit form so they land in the right section.
